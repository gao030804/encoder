# Encoder + RVQ：Design Compiler 综合约束与 PrimeTime PX 功耗测试分析总结

> 整理日期：2026-10-16  
> 项目：[`gao030804/encoder`](https://github.com/gao030804/encoder)  
> 工艺：TSMC 28HPC+，BWP30 基础 + HVT + LVT 标准单元库；使用已生成的 SRAM 宏  
> 当前阶段：**仅做逻辑综合，生成可用门级网表，并结合门级仿真 VCD/SAIF、PrimeTime PX（PTPX）评估功耗；尚未进行 CTS、布局布线和寄生参数提取。**

## 1. 核心结论

1. **综合时应该保留时钟不确定性**，但当前 `set_clock_uncertainty = CLK_PERIOD * 0.05` 在 50 MHz 下等于 **1.0 ns**，缺少明确的时钟抖动 / 时钟偏斜预算依据。建议先使用固定值 **Setup = 0.20 ns、Hold = 0.05 ns** 作为 *实验起点*，再做与原约束的对比。它们不是 TSMC 官方固定值，最终须根据时钟源、工艺库和实际 CTS 数据调整。
2. **最需要优先修复的问题并不只是 1 ns uncertainty**：当前脚本对几乎全部非 `clk` 输入统一施加 20% 周期输入延迟，对所有输出统一施加 20% 周期输出延迟及负载，未区分复位、scan、PHY/Flash 和同步接口，可能导致错误时序假设与额外面积/功耗。
3. **SRAM 宏建议只放在 `link_library`**，标准单元库放在 `target_library` 用于逻辑映射；SRAM 是 RTL 中明确实例化的硬宏，需要检查 reference、功耗模型和活动覆盖率。
4. **当前 `mesh_icg_tech.v` 并非真实工艺 ICG**，而是 `negedge FF + AND` 的临时实现；适合功能验证，不宜直接把其功耗作为真实 ICG 功耗的最终结论。应以经确认的 TSMC 库单元替换，并检查功能模式/扫描模式与门控时序。
5. **当前默认是 TT 综合**（若 `CORNER` 环境变量未指定），不是默认 SS。建议用 **TT 综合 + TT 功耗库**建立一致、可重复的典型 PPA 基线，另以 SS 评估 Setup 风险。综合 Corner 和 PTPX 分析 Corner 是两个独立概念。
6. 目前得到的是 **Pre-layout 功耗估计**；由于没有 CTS、真实时钟树、提取互连与 SDF，绝对功耗仍有局限，适合相同条件下的相对优化对比。

### 综合 Corner 的选择

截图中 `dc_setup.tcl` 的逻辑大致为：

```tcl
if {(![info exists ::env(CORNER)] || $::env(CORNER) == "tt")} {
    set CSUF "tt0p9v25c"
} else {
    set CSUF "ssg0p81v125c"
}
```

因此 **没设置 `CORNER` 或设为 `tt` 时使用 TT**；其他值均进入 SS 分支，存在误配置风险。建议明确接受 `tt` / `ss` 并对未知值报错。实际 .db 名称、PVT 与支持的 operating conditions 仍应以服务器工艺库为准。

参考写法：

```tcl
if {![info exists ::env(CORNER)]} {
    set CORNER "tt"
} else {
    set CORNER $::env(CORNER)
}
switch -- $CORNER {
    tt { set CSUF "tt0p9v25c" }
    ss { set CSUF "ssg0p81v125c" }
    default { error "Unsupported CORNER=$CORNER (use tt or ss)" }
}
```

## 3. 时钟不确定性：保留，但不要无依据按周期 5% 固定

现有：

```tcl
set_clock_uncertainty [expr $CLK_PERIOD * 0.05] [get_clocks $CLK_NAME]
```

其含义：

| 时钟频率 | 周期 | 原 5% uncertainty |
|---|---:|---:|
| 30 MHz | 33.33 ns | 约 1.667 ns |
| 50 MHz | 20.00 ns | 1.000 ns |
| 100 MHz | 10.00 ns | 0.500 ns |

固定比例并不一定能合理对应时钟抖动、预期偏斜和裕量。对于目前 50 MHz、尚无 CTS 的**探索性功耗评估**，建议先测试：

```tcl
create_clock -name $CLK_NAME -period $CLK_PERIOD [get_ports clk]
set_clock_uncertainty -setup 0.20 [get_clocks $CLK_NAME]
set_clock_uncertainty -hold  0.05 [get_clocks $CLK_NAME]
set_clock_transition 0.10 [get_clocks $CLK_NAME]
```

这不是承诺 0.2 ns 一定足够；它只是**明确可复现的暂定时序预算**。物理实现前应由 PLL/时钟源抖动、Pre-CTS skew 预算、OCV、CTS 和签核要求重新计算。

- Setup uncertainty 增大可能加大优化压力，改变单元尺寸、缓冲和面积/功耗；不一定每次都会改变网表。
- Hold uncertainty 与 Setup 分开约束，不能通过调小 uncertainty 把实际 Hold 问题视为已经修复。
- 没有 CTS 时，综合 Hold 报告并非最终 Hold 签核；当前优先修复时钟约束错误和门控半周期路径。
- 建议对照 1.0 ns 与 0.2 ns 的 WNS/TNS、reference、面积、Buffer 和用同一活动场景得到的 PTPX 功耗。

## 4. IO 约束：需要优先按接口重新分类

现有代码把除 `clk` 以外的全部输入看成相同的同步数据输入：

```tcl
set DATA_INPUTS [remove_from_collection [all_inputs] [get_ports clk]]
set INPUT_DELAY  [expr $CLK_PERIOD * 0.20]
set OUTPUT_DELAY [expr $CLK_PERIOD * 0.20]
set_input_delay  $INPUT_DELAY  -clock [get_clocks $CLK_NAME] $DATA_INPUTS
set_input_transition 0.10 $DATA_INPUTS
set_output_delay $OUTPUT_DELAY -clock [get_clocks $CLK_NAME] [all_outputs]
set_load 0.05 [all_outputs]
```

### 为什么不合适

GitHub 当前顶层有 `rst_n`、`mesh_scan_test_en`、`octal_phy_clk`、`octal_phy_rst_n`、`octal_rx_*`、`flash_*`、`input_wr_*`、`param_rd_*` 等性质不同的端口。它们不应无差别地承受同一组输入/输出延迟。

建议按接口区分：

| 接口 | 推荐约束思路 |
|---|---|
| `clk` | 定义主时钟 |
| `rst_n` | 异步复位；复位释放仍需按实际电路检查 recovery/removal，不应随意一律 false-path |
| `mesh_scan_test_en` | 功能模式可 `set_case_analysis 0`；扫描模式另外验证与约束 |
| 明确同步于主时钟的输入 | 设置 `-max` / `-min` input delay、input transition |
| 明确同步于主时钟的输出 | 设置 `-max` / `-min` output delay、合理 output load |
| PHY / 外部独立时钟 | 如被实际实例化和使用，需定义相关 clock、CDC 与时序关系 |
| QSPI/Flash | 按器件时序、输出时钟及相位关系建立独立接口约束 |
| 监测/调试输出 | 根据是否为真实芯片引脚决定是否施加片外负载 |

**示例（仅当这些端口已确认与 `CORE_CLK` 同步时可用）：**

```tcl
set SYNC_INPUTS [get_ports {
    start
    input_wr_valid
    input_wr_addr*
    input_wr_data*
    input_wr_strb*
}]
set_input_delay -max 4.0 -clock CORE_CLK $SYNC_INPUTS
set_input_delay -min 0.0 -clock CORE_CLK $SYNC_INPUTS
set_input_transition 0.10 $SYNC_INPUTS
```

`4.0/0.0 ns` 仅是演示性的暂定预算；应按外部发送/接收设备的时序重新确定。**不要把所有其他端口简单设置为 false path，不能为获得干净报告而掩盖实际路径。**

## 5. 标准单元库、SRAM 宏与 `dont_touch`

当前 `.db` 配置包含：

- 标准单元库 `STD_LIBS`：基础 + HVT + LVT。
- SRAM 宏 `SRAM_LIBS`：六种由 TSMC28HPC SRAM Compiler 生成的宏。

原脚本类似：

```tcl
set_app_var target_library [concat $STD_LIBS $SRAM_LIBS]
set_app_var link_library [concat [list *] [concat $STD_LIBS $SRAM_LIBS] $SYNTH_LIBS]
```

建议改成标准单元映射、SRAM 宏链接更明确的配置：

```tcl
set_app_var target_library $STD_LIBS
set_app_var link_library [concat [list *] $STD_LIBS $SRAM_LIBS $SYNTH_LIBS]
set_app_var synthetic_library $SYNTH_LIBS
```

SRAM 是 RTL 中已实例化的硬宏，建议保留 `set_dont_touch`，同时重点检查：

1. SRAM 模块名称/`ref_name` 是否与 `.db` 一致、有无 unresolved reference。
2. SRAM 是否确实保留为宏，而非在综合时变为大量触发器。
3. `report_area` 是否按目标宏库反映宏面积。
4. PTPX 的 SRAM 库是否包含实际可用的 read/write/internal/leakage power 数据；**成功 link 不代表成功建模 SRAM 功耗**。
5. SRAM 时钟、CS/CE、WE、地址、数据活动是否被有效标注。
6. 同时使用 HVT/LVT 时，要统计实际选择了多少高/低阈值单元；不能因为加载了 HVT 库就认为大部分非关键路径已自动选 HVT。

## 6. Mesh ICG：当前是临时技术封装，不是真实工艺单元

代码位置：

- [`clock_gate/mesh_icg.v`](https://github.com/gao030804/encoder/blob/main/clock_gate/mesh_icg.v)
- [`clock_gate/mesh_icg_tech.v`](https://github.com/gao030804/encoder/blob/main/clock_gate/mesh_icg_tech.v)
- [`adress/conv1d_controller.v`](https://github.com/gao030804/encoder/blob/main/adress/conv1d_controller.v)

当前 `mesh_icg_tech.v`：

```verilog
reg en_latched;
always @(negedge clk_i) begin
    en_latched <= en_i | test_en_i;
end
assign gclk_o = clk_i & en_latched;
```

这是可综合的 **下降沿 FF + AND**，不是工艺库原生集成 ICG。注意：

- FF+AND 与“低电平透明锁存器 + AND”在使能更新时序上**不完全等价**。
- `en_i` 到下降沿 FF 需要检查半周期时序；`test_en_i` 不应悬空。
- 综合器不一定把 FF+AND 自动替换成专用 ICG，不能仅凭模块名 `mesh_icg_tech` 认为已经映射真实 ICG。
- 用其生成的 PTPX 结果仅代表这版临时门控实现的功耗。

**更可靠的 ASIC 流程：**

1. 从已授权的 28HPC 工艺库中确认具体 ICG 单元、引脚、使能极性、测试引脚和对应的 `.db` / 仿真模型。
2. 在 `mesh_icg_tech.v` 封装中例化真实 ICG；不要臆造工艺单元名。
3. 以相应库进行综合链接，检查其不被 `dont_use` 屏蔽，并核对 `report_reference`、门控时序、波形与扫描测试模式。
4. 重新门级仿真及 PTPX 功耗对比；如果后续进入 CTS，再检查驱动强度、Clock Tree、Skew 和签核时序。

当前 `conv1d_controller.v` 中门控使能为 `mesh_phase_active && mesh_ce`，只对 Mesh 相关管线停钟，其他 Controller/Accumulator/SRAM 等仍由主时钟控制。这与“先做粗粒度 Mesh ICG，再做内部细粒度优化”的计划相符。

## 7. DRC 约束、层次与综合命令

### `set_max_fanout 16`

可能促使工具插入额外 Buffer/复制逻辑，不过 DC 中 fanout 属性不一定等价于物理引脚数。建议做保留/移除对照，在不违反库 DRC 的前提下看 Buffer 数量、面积和功耗变化，不应直接宣称删除后一定省功耗。

### `set_max_transition 0.50`

可以保留作为实验起点，须核对 Liberty 中的 max_transition、电容负载和真实 SRAM 接口约束，最终保持 DRC 合规。

### `set_load 0.05`

需要先查 Liberty 的 `capacitive_load_unit`。若单位为 pF，即 50 fF；给大量宽总线监测接口统一施加同样负载可能不合理。应区分真实 I/O 引脚、模块间连线和纯调试口。

### 综合流程

```tcl
compile_ultra -no_autoungroup
set_fix_multiple_port_nets -all -buffer_constants
compile_ultra -incremental -no_autoungroup
```

命令本身可以使用。后续建议做独立 A/B 实验：

- `-no_autoungroup` 与允许自动展开的 QoR 对比。
- 有/无增量综合的 WNS、TNS、面积、Buffer 和功耗对比。
- 保证实验其余输入与库一致，避免把逻辑展开或优化激进程度带来的差异误记成 RTL 架构收益。

## 8. 推荐约束片段（**不是完整 signoff SDC**）

> 仅定义基本主时钟和暂定设计规则；完整 IO、可能存在的独立时钟、Flash/PHY、扫描、复位等需按实际接口补齐。

```tcl
# ===========================================
# Pre-layout DC / PTPX experiment baseline
# ===========================================
if {![info exists CLK_PERIOD]} {
    set CLK_PERIOD 20.0
}
set CLK_NAME CORE_CLK

create_clock -name $CLK_NAME -period $CLK_PERIOD [get_ports clk]
set_clock_uncertainty -setup 0.20 [get_clocks $CLK_NAME]
set_clock_uncertainty -hold  0.05 [get_clocks $CLK_NAME]
set_clock_transition 0.10 [get_clocks $CLK_NAME]

# 初步 DRC；需对照所用 Liberty 规则
set_max_transition 0.50 [current_design]

# 暂不强制全局 max_fanout=16
# 不对所有输出统一 set_load 0.05
# 不对所有非 clk 输入统一施加 20% input delay
# 不对所有输出统一施加 20% output delay

# 仅用于功能模式的约束；DFT另行验证
set_case_analysis 0 [get_ports mesh_scan_test_en]

puts "Clock period: $CLK_PERIOD ns"
puts "Setup uncertainty: 0.20 ns"
puts "Hold uncertainty: 0.05 ns"
```

**使用条件：** `mesh_scan_test_en` 在功能门级仿真中仍需被明确驱动为 0；SDC 的 `set_case_analysis` 不会替代仿真激励。对于异步复位释放及使用中的 `octal_phy_clk`，应另行建立时序检查，不能仅因当前阶段只测功耗而忽略。

已存在 `report_qor`、`report_area`、`report_timing`、`report_constraint`、`report_reference` 和 `report_power`。可补充：

```tcl
redirect -file "$REPORT_DIR/clocks.rpt" {
    report_clock
}
redirect -file "$REPORT_DIR/check_timing.rpt" {
    check_timing
```

## 10. Pre-layout PTPX 功耗测试流程及局限

建议工作流：

```text
TSMC 28HPC+ STD cell .db + SRAM .db
                     |
              Design Compiler
             TT / 50 MHz / SDC
                     |
             门级综合网表 (.v)
                     |
      门级功能仿真（相应库 Verilog 模型）
      同一批真实 PCM / 相同激励 / 相同时间窗口
                     |
                 VCD / SAIF
                     |
     PrimeTime PX（匹配的 TT STD + SRAM 功耗库）
                     |
    按层级统计 Mesh / Controller / SRAM / RVQ 等
      internal / switching / leakage / clock
                     |
          分析 P_avg、E_frame 与功耗差异
```

对 PTPX：

```tcl
report_power -hierarchy
report_switching_activity
```

根据版本和运行方式，还要核对 VCD/SAIF 的层级映射和活动注入日志，尤其是 SRAM 控制引脚、时钟以及关钟时段的波形。

| 功耗组成 | 这一阶段的可信度 |
|---|---|
| 标准单元内部动态功耗、Leakage | 在指定工艺库/PVT 下可获得初步估计 |
| SRAM 内部读写功耗 | 依赖对应 SRAM 宏的功耗表及正确激励 |
| 组合逻辑毛刺功耗 | 无 SDF / 实际互连时可能不准确 |
| 真正工艺 ICG 功耗 | 必须先替换临时 FF+AND 实现 |
| 时钟树 Buffer 功耗 | 无 CTS，不能视为已经完整计入 |
| 后布局互连功耗 | 没有提取寄生，难以精确估算 |

建议统一能量口径：

\[
E_{\mathrm{frame}} = \int_{t_{\mathrm{start}}}^{t_{\mathrm{done}}} P(t)\,dt,
\qquad
P_{\mathrm{avg}} = \frac{E_{\mathrm{frame}}}{T_{\mathrm{frame}}}
\]

明确统计窗口是否包含：Flash 一次性 Boot、帧间空闲、PCM 搬运、Encoder 计算、RVQ、结果 DMA。**不同统计窗口不能直接比较平均功率**，尤其门控优化可能主要作用在空闲时段。

原项目文档中的 50 MHz 功能回归约为每帧 `531524` 周期，即约 `10.63048 ms`，该数据来自本地功能级回归，**不能视作服务器 STA 或后布局功耗验证**。

## 11. 建议修改优先级

| 优先级 | 项目 | 建议 |
|---|---|---|
| P0 | Mesh ICG 真实映射 | 用经确认的 TSMC 原生 ICG 替换 FF+AND 临时实现，或明确把当前结果标为临时实现 |
| P0 | 主时钟/门控时钟/PHY 时钟完整约束 | 先确认实际时钟域，避免漏约束与错误的普通数据输入约束 |
| P0 | IO 约束分类 | 区分同步 I/O、异步复位、扫描、Flash/PHY、调试观察口 |
| P0 | SRAM 库与模型 | 标准单元 target、SRAM link；确认功耗模型及活动覆盖 |
| P1 | Clock Uncertainty | 以 0.20/0.05 ns 作为起点与原 1.0 ns 比较 |
| P1 | Max Fanout/Transition/Load | 删除非必要的全局激进约束，按真实需求调整 |
| P1 | QoR 与功耗报告 | 补充 clocks、check_timing、reference、ICG、SRAM 和 annotation 覆盖率 |
| P2 | 综合层次和增量综合 | 分别实验 `-no_autoungroup`、增量编译对 QoR 的影响 |
| P2 | Corner 对比 | TT 建主基线，SS 补充 Setup；未来 CTS/PR 采用 MCMM 检查 |

### 推荐三组实验

| 实验 | 配置 | 目的 |
|---|---|---|
| A：原始基线 | 原有 RTL + 原综合/SDC | 保存历史可复现结果 |
| B：约束优化 | 相同 RTL + 改进的 SDC、库组织 | 区分脚本约束造成的额外面积/功耗 |
| C：ICG 映射 | B 的约束 + 真实工艺 ICG | 验证真实门控节能收益 |

所有实验使用相同 **50 MHz、TT 功耗 Corner、PCM 激励、VCD 窗口、SRAM 宏和功耗模型**，同时记录 WNS、TNS、面积、Buffer 数量、SRAM 活动、动态功耗、漏电功耗和 `E_frame`。对比时必须让不同版本的输出比对通过。

---

## 12. 最终建议

- **保留 uncertainty，但当前 5%=1 ns 没有充分依据。** 先以 Setup `0.20 ns`、Hold `0.05 ns` 做实验起点，通过时序与功耗对照确定是否需要调整。
- 现阶段优先修复 **ICG 真实映射、IO/时钟约束分类以及 SRAM 功耗库/活动覆盖率**；这三件事通常比简单调小 uncertainty 更直接影响功耗报告的可信度。
- 暂不做 CTS/PR 并不阻止 PTPX 对比，但应将结果明确标注为 **Pre-layout / Pre-CTS Power Estimate**，不能当作最终芯片功耗或 signoff。
- 不要为了低功耗而忽略 `check_timing`、门控使能半周期时序或功能/扫描模式的一致性。
